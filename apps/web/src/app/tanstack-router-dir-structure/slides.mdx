<PersonalContentSlide title="3案を考えた">

1. **features に寄せる**
2. **routes に全部押し込む**
3. **ハイブリッド**

- → 結果的に **3つ目（ハイブリッド）** を採用

</PersonalContentSlide>

<PersonalContentSlide title="案① features に寄せる">

<CodeBlock lang="text" code={DIR_OPT_FEATURES} />

- `Page` まで features に集約、routes は読むだけの薄い wrapper
- シンプルだが、`-` コロケーションなど **TanStack Router の機能を活かしきれない**

</PersonalContentSlide>

<PersonalContentSlide title="案② routes に全部押し込む">

<CodeBlock lang="text" code={DIR_OPT_ROUTES} />

- `-` prefix で全部 routes に詰め込める → **機能はフル活用**
- ただしルートが肥大化して **ぐちゃぐちゃ**になりがち

</PersonalContentSlide>

<PersonalContentSlide title="案③ ハイブリッド（採用）">

<CodeBlock lang="text" code={DIR_OPT_HYBRID} />

- TanStack Router 依存部分だけ routes、ロジックの実体は features
- 機能はフル活用しつつ、**Router 依存を routes に閉じ込められる**いいとこ取り

</PersonalContentSlide>

<PersonalContentSlide title="ディレクトリ構成">

<CodeBlock lang="text" code={DIR_STRUCTURE} />

- routes は **宣言だけ**、ロジックの実体は features に
- routes と features の分担が **ディレクトリ構造で見える**形に

</PersonalContentSlide>

<PersonalContentSlide title="なぜ fallbacks が要る？">

- loader で `ensureQueryData`、component は `useSuspenseQuery` で読む
- loader が pending になると `pendingComponent`、失敗すると `errorComponent` が出る
  - `ensureQueryData` で先に埋めておくので、`Page` 側は「取得済み前提」で書ける
- `-components/fallbacks/` に中身を用意する
- prefetch するルートだけなので **「必要なルートのみ」**

</PersonalContentSlide>

<PersonalContentSlide title="コードで見ると">

<CodeBlock lang="tsx" code={ROUTE_EXAMPLE} />

- `index` は宣言だけ、`Page` は「取得済み前提」で `useSuspenseQuery`
- loader の `ensureQueryData` が **routes と features の繋ぎ目**

</PersonalContentSlide>

<PersonalContentSlide title="採用してどうなった">

- features のベストプラクティスと TanStack Router の機能、**両方を活かせる形**に
- TanStack Router の影響が **routes に閉じている**ので、今後の変更も加えやすい
- 実体は **Router 非依存** → 変更・テスト・再利用がしやすい
- 反面、component の置き場が **3 つ**に → **AI が迷わない整備**が重要に

</PersonalContentSlide>

<PersonalContentSlide title="2 本から学んだこと">

- 2 本に共通していたのは **「`createServerFn` の中身は薄く保つ」** という点
- → ロジックは serverFn の外に出し、wrapper は薄い層に留める
- さらに **schema / server / function** に分けると良い
- https://tanstack.com/start/v0/docs/framework/react/guide/server-functions#file-organization

</PersonalContentSlide>

<PersonalHeadingSlide>

serverFn、どこに置く？

</PersonalHeadingSlide>

<PersonalContentSlide title="また3案を考えた">

1. **src/server に寄せる**
2. **routes にハイブリッド**
3. **features に寄せる**

</PersonalContentSlide>

<PersonalContentSlide title="案① src/server に集約">

<CodeBlock lang="text" code={SERVER_FN_SRC} />

- serverFn を横断の `src/server` に全部集約
- 分かりやすいが、管理する場所が **3 つ目**に増える

</PersonalContentSlide>

<PersonalContentSlide title="案② routes にハイブリッド">

<CodeBlock lang="text" code={SERVER_FN_ROUTES} />

- wrapper だけ routes、schema / logic は features
- serverFn は `useServerFn` で **component（features 側）から呼べる**
- → wrapper を routes に置くと **features が routes に依存する逆転構造**になる

</PersonalContentSlide>

<PersonalContentSlide title="案③ features に集約">

<CodeBlock lang="text" code={SERVER_FN_FEATURES} />

- wrapper も含めて `features/<domain>/server` に全部
- 管理対象が増えず、「**ロジックの処理**」という性質とも合う

</PersonalContentSlide>

<PersonalContentSlide title="features 寄せを採用">

- 構成では「ハイブリッド」が勝った。今回は **3つ目（ハイブリッド）を蹴った**
- `createServerFn` の wrapper は `Page` のような薄い層ではなく、**実体** だった
- routes に切り出すと、ドメインが routes と features の **2 箇所に分散** する
- → 軸は同じ「実体は features」。wrapper の見立てだけ変えて **3つ目（features 寄せ）** を採用

</PersonalContentSlide>

<CodeBlock lang="text" code={DIR_STRUCTURE_WITH_SERVER} />

- features に `server/`（schema / function / logic）を追加しただけ
- routes は変わらず **宣言に専念**、軸はブレていない

</PersonalContentSlide>
